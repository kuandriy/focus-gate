**Time marker:** 2026-04-30..2026-05-07

**Topics:** memory frontmatter format, chapter What/Why structure, weight derivation from chapter coverage, migration with v1.bak backup

### What
A v2 memory is one Markdown file: YAML-ish frontmatter + a body of
`## Chapter N — <date> — <title>` blocks, each with `### What` and `### Why`
subsections. Chapters never edit; corrections are appended as new chapters with
their own time marker and metadata. The frontmatter aggregates every chapter's
metadata as the per-memory index: timeMarkers (append order, deduplicated),
interests and topics (each as `name@weight` pairs where the weight is computed at
write time as `chapters_mentioning / total_chapters`, saturated at 1.0 and floored
at 0.1), and assets (case-insensitive union, alphabetically sorted). The id is
immutable. Validation enforces ≥1 chapter, each with non-empty What and Why; the
title is ≤80 runes. v1 files (single-doc with `## What we did` / `## Why`) migrate
to a single Chapter 1 of v2; the original is preserved as `<file>.v1.bak` and the
migration is invoked explicitly via `fg: memory migrate-v1` rather than running
on first load.

### Why
Append-only is the audit trail. Five years from now, the second half of a story
may matter more than the first, but neither version is rewritten retroactively —
that's how human professional knowledge actually accumulates: by doing, by
repeating, by occasionally being wrong and noticing. The aggregate index lets the
manifest layer support fast lookup without re-parsing chapter bodies on every
prompt. Weight derivation from chapter coverage is a soft prior: an entry mentioned
in every chapter is more central to the story's main thrust than one mentioned
once. Weights multiply cosine during surface ranking but never veto a match. The
explicit-only migration model trades automatic convenience for a clean diff that
the user reviews before any data lands in v2 form.
